# `artcode/tools/base.py` 阅读指南

## 一、这个文件是做什么的

这个文件不实现具体工具，而是规定“所有工具共同使用什么数据、遵守什么接口”。

可以把它理解成工具系统的合同：

- 工具运行时能拿到什么环境？
- 工具执行前要提供什么预览？
- 准备成功后返回什么？
- 每个具体工具必须实现哪些属性和方法？

文件只有约 50 行，但对理解权限系统很重要。

## 二、`ToolExecutionContext`：工具运行环境

```python
@dataclass(frozen=True)
class ToolExecutionContext:
    path_policy: AllowedPathPolicy
    max_result_bytes: int = MAX_RESULT_BYTES
    command_timeout_seconds: float = 10.0
    default_cwd: Path | None = None
```

它集中保存所有工具共享的运行约束：

- `path_policy`：哪些目录允许访问。
- `max_result_bytes`：工具最多返回多少内容。
- `command_timeout_seconds`：命令最多运行多久。
- `default_cwd`：命令和相对路径默认从哪里开始。

### 为什么要用 Context

如果没有它，每个工具都要分别接收允许目录、超时和结果限制，参数会越来越多，也容易出现工具之间规则不一致。

Context 把一次运行共享的环境打包成一个对象。

### 语法：`Path | None`

表示值可以是 `Path`，也可以是 `None`。

`None` 表示“目前没有设置值”，类似其他语言中的 `null`。

## 三、`ToolPreview`：执行前预览

```python
@dataclass(frozen=True)
class ToolPreview:
    tool_name: str
    summary: str
    target: str
    requires_confirmation: bool
```

它包含：

- 工具名称。
- 本次操作摘要。
- 影响目标。
- 是否要求确认。

例如一次写文件调用可以产生类似预览：

```text
工具：write_file
摘要：创建文本文件
目标：/允许目录/demo.py
需要确认：是
```

这正是未来展示给用户审批的信息基础。

### 当前状态

这个结构已经存在，但 ch04 之后的 Agent Loop 没有真正使用 `requires_confirmation` 发起确认。

换句话说：数据准备好了，审批链路还没有接起来。

## 四、`PreparedToolCall`：准备完成的调用

```python
@dataclass(frozen=True)
class PreparedToolCall:
    tool: Tool
    arguments: dict[str, Any]
    preview: ToolPreview
```

它表示：

- 已经找到具体工具。
- 参数已经解析和校验。
- 目标路径等信息已经标准化。
- 执行预览已经生成。
- 但真正副作用还没有发生。

这是最适合进行权限判断的时刻。

## 五、`Protocol`：接口合同

```python
class Tool(Protocol):
```

`Protocol` 可以理解成“只要长得符合这些要求，就可以被当作 Tool 使用”。

一个具体工具需要具备：

- `name`
- `description`
- `parameters_schema`
- `requires_confirmation`
- `prepare(...)`
- `execute(...)`

它不要求具体工具必须继承某个共同父类。Python 更关注对象是否提供了所需能力，这种思想常被称为鸭子类型：

> 如果它走起来像鸭子、叫起来像鸭子，就可以把它当鸭子。

`Protocol` 则给这种灵活方式补上了静态类型提示。

## 六、方法签名怎么读

```python
def prepare(
    self,
    arguments: dict[str, Any],
    context: ToolExecutionContext,
) -> PreparedToolCall | ToolResult:
```

翻译为：

> `prepare` 接收参数字典和执行环境，成功时返回准备好的工具调用，失败时返回工具结果对象，其中包含结构化错误。

这里没有用异常表示所有参数错误，而是把可预期的工具失败包装成 `ToolResult`，方便回灌给模型。

## 七、异步方法怎么读

```python
async def execute(...)
```

表示执行过程可能等待：

- 文件 I/O。
- 子进程。
- 超时计时。

调用它时需要：

```python
result = await tool.execute(...)
```

`async def` 创建协程函数，`await` 等待协程完成。

## 八、`...` 是什么

Protocol 方法体中的：

```python
...
```

叫 Ellipsis。这里的意思是“只声明方法形状，不在此提供实现”。

具体实现由 `ReadFileTool`、`WriteFileTool` 等类提供。

## 九、ch06 需要思考的设计问题

权限信息应该放在哪一层，需要保持边界清楚：

- 工具自身知道本次操作目标和摘要。
- 权限策略知道什么条件应允许、询问或拒绝。
- TUI 知道如何向用户展示问题并收集答案。
- Agent Loop 知道流程是否继续。

不建议让每个具体 Tool 自己直接向终端询问，因为这样工具会依赖 TUI，自动化测试和未来替换界面都会更困难。

## 十、阅读练习

打开任意一个具体工具，例如 `WriteFileTool`，寻找：

1. 它的 `name`。
2. 它的 `requires_confirmation`。
3. 它的 `prepare`。
4. 它的 `execute`。
5. `prepare` 在哪里创建 `ToolPreview`。

不需要读懂写文件细节，只需确认具体工具确实遵守了这份“合同”。
