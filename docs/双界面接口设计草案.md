## 1. 用户目标与设计范围

终端 TUI 和 macOS GUI 使用同一套 ArtCode 能力。用户能实时看到主 Run、Subagent Run、单次工具调用、审批、Shell 输出、压缩及后台 Task 的实际状态，而不仅是最终模型回复。两种界面可采用不同布局，但不得各自复制业务状态及权限规则。

本草案覆盖类型化应用 Interface、完整执行活动流、状态查询、Python stdio App Server 和 TUI 接入。Electron 界面、安装包、常驻后台、两端同时控制同一 Run、跨后端重启的完整活动回放，需要后续产品决策，不作为本次接口施工的默认承诺。接口为这些能力保留明确对象标识。

## 3. 职责与依赖

TUI 通过类型化操作调用 Application，并独立订阅活动。GUI 通过 Electron 主进程与 Python App Server 通信；App Server 把协议请求翻译成相同 Application 操作。

- Application 拥有客户端操作协调、活动关联、订阅游标与展示投影。
- Agent、Tool、Workspace、Subagent、Skill 各自在自己的状态变化处产生所属活动，通过注入的观察接口向上报告。
- 低层模块不导入 Application、TUI、Electron 或协议实现；观察接口按既有依赖方向定义，Application 注入转换 Adapter。
- Session 继续拥有 Transcript、Prompt 和持久化。展示投影可重建，不成为第二份权威对话历史。
- Subagent 继续拥有 Task 调度和子 Run；观察能力不改变 Subagent 禁止再次委派、禁止交互审批等规则。
- UI 事件表示实际执行活动及公开文字输出，不包含 Provider 的内部 reasoning、Protocol Metadata 或完整内部 Prompt。

事件产生不能依赖前端正在等待某个请求的返回。执行操作、协议读写、事件订阅应分别推进，主 Run 在等待前台子任务时，界面仍能收到子任务事件和提交取消操作。

## 4. 三类实际接口

方法名为拟议契约，供审阅；实现前需要确认公开契约变更。

### 4.1 控制与查询

| 方法组 | 拟议方法 | 范围及行为 |
| --- | --- | --- |
| 协议与启动 | `initialize`、`application.open`、`application.close` | 协商版本和能力，按 Workspace/配置/SessionSelection 启动；启动期也能发送 MCP 审批和失败事件 |
| 状态与历史 | `application.snapshot`、`session.history` | 返回面向用户的类型化状态、分页已提交事实和观察游标；过滤不透明协议字段 |
| 执行 | `run.start`、`run.cancel` | 接受 chat/plan/act 意图；act 使用后端最近有效计划；取消精确 Run，准备期间可用 operation_id 取消 |
| 人工交互 | `interaction.list`、`interaction.respond` | 列出/回答启动确认、工具审批、退出选择、Worktree 丢弃确认；校验类型、对象、有效期与是否已处理 |
| 权限 | `permissions.get`、`permissions.set`、`sandbox.set` | 复用现有权限与隔离语义，声明新配置对当前冻结 Run 与后续 Run 的影响 |
| Skill | `skills.list`、`skills.activate`、`skills.clear`、`skills.run` | 保留发现、激活及 Shared/Isolated 执行语义；Isolated 活动可观察但不创建 Task |
| Task | `tasks.list`、`tasks.get`、`tasks.cancel`、`tasks.background` | 操作核心已有 Task；子任务仍由主 Agent 的 agent 工具创建，不顺便新增 GUI 直接任意委派能力 |
| MCP | `mcp.status` | 只读服务器/发现/激活状态；已有模型搜索激活路径保持原有能力限制，不给 GUI 增加任意远程调用捷径 |
| 上下文与记忆 | `context.compact`、`memory.status` | 复用手动压缩及已有记忆状态；压缩和自然完成后的异步记忆更新可观察 |
| Worktree | `worktrees.list`、`worktrees.discard` | 复用列表、成果状态及精确确认；不新增自动合并、推送或自动丢弃 |
| 展示内容 | `outputs.read` | 按归属与范围回读已保存的工具输出；报告截断、已过期或不支持的内容 |
| 本地显示 | TUI/GUI 各自处理 | 字号、折叠、滚动和纯清屏不作为核心业务；现有 /clear 的 Skill 行为在正式决策前保持，不能静默修改 |

`session.history` 的分页、`mcp.status` 的完整状态投影及 `outputs.read` 的用户侧统一入口属于待补能力，不能把现有 snapshot 的任意字段直接当成已完备实现。

启动选择继续覆盖新建、最近可写、指定 Session。首版每个打开的 Application 绑定一个 Workspace 和 Session；不通过修改全局 cwd 切换执行归属。跨项目会话索引、多个同时活动的 Session 和配置编辑器另行确定。

对同一 Session 的新执行或压缩，在已有前台操作期间先返回明确 busy 状态；查询、审批答复和取消仍可处理。运行中追加目标/排队/steering 需要另行定义，不把重复点击偷偷解释成新 Run。

### 4.2 持续订阅

`events.subscribe` 接收 Application/Session 范围与可选游标，持续返回活动；`events.unsubscribe` 只解除观察，不等于取消执行。后台 Task 的事件在主 Run 结束后仍继续发布，直到 Task 到达终态或所属 Application 按约定关闭。

查询方法不能取走模型 Notice、推进工具、改变权限或制造重复 Transcript 提交。

### 4.3 快照与观察恢复

快照包含当前 Run、Task、未解决交互、保留范围内的消息和工具条目状态（包括终态）、必要文字预览，以及同一观察时点的游标。实现先登记订阅再取得一致快照，或使用等价的原子水位机制，避免快照与订阅之间漏事件。

重同步时用快照替换该观察范围的旧展示投影。若某条目已超出保留范围，明确标记详情不可恢复，不能从“快照里没有它”推断成功，也不能继续保留旧的永久运行状态。已提交对话事实仍可从 Session 历史重新取得。

首版使用进程内有界活动保留。客户端断订阅后，在同一后台仍存活且游标有效时补齐事件；游标过期返回明确 gap/resync_required，客户端重新获取快照。后台重启使用新的 instance_id，旧游标不继续使用。

这不是承诺后台崩溃后恢复正在执行的 Task。现有 Task 不跨进程恢复，历史临时活动与输出也不保证跨重启保留。若用户要求完整历史执行树，应另行批准展示活动存储与保留策略。

## 5. 事件关联格式

```json
{
  "schema_version": 1,
  "instance_id": "backend-1",
  "sequence": 42,
  "type": "tool.started",
  "operation_id": "operation-1",
  "session_id": "session-main",
  "run_id": "run-child-1",
  "task_id": "task-1",
  "parent_run_id": "run-main",
  "parent_tool_call_id": "call-agent-1",
  "tool_call_id": "call-read-1",
  "item_id": "item-17",
  "source": {"kind": "subagent", "name": "reader"},
  "payload": {"tool_name": "read_file", "target": "README.md"}
}
```

- `session_id` 标识界面所观察的主 Session；子 Run 的临时 Session ID 不冒充主 Session 的持久化历史标识。
- `run_id` 标识实际执行；子 Run 与主 Run 不共用编号。`task_id` 仅用于真实 Subagent Task。
- `parent_run_id`、`parent_tool_call_id` 表示创建关系；手工触发的 Isolated Skill 可关联 operation_id，没有父 Run 时为 null，不虚构 Task。
- `item_id` 区分同一 Run 内不同消息或工具展示条目。模型给出的 tool_call_id 只在所属 Run 中使用，不假设跨 Run 唯一。
- `instance_id + sequence` 用于同一后台观察顺序与去重；时间戳可用于展示，但不用于判定因果关系。
- 启动前尚不存在 Session/Run 的交互，以 operation_id 关联，其余字段允许 null。
- 来源标识表示真实模块行为；“正在思考”最多展示为等待模型响应，不据此猜测模型内部动作。

## 6. 事件目录与终态

| 类别 | 拟议事件 | 关键语义 |
| --- | --- | --- |
| 执行 | `run.preparing`、`run.started`、`run.phase_changed`、`run.finished` | 结束原因保留自然完成、限制、取消、模型失败、长度结束、无法继续 |
| 消息 | `message.started`、`message.delta`、`message.finished` | 指明来源和消息条目；标记完成/中断及是否已提交，不能混入另一 Agent 的气泡 |
| 单工具 | `tool.requested`、`tool.started`、`tool.output`、`tool.progress`、`tool.finished` | 请求不等于已执行；终态含成功、拒绝、非法参数、失败、超时、取消或未启动 |
| 交互 | `interaction.requested`、`interaction.resolved` | 带唯一交互 ID、关联对象与可选回答；只能有效处理一次 |
| 子任务 | `task.created`、`task.started`、`task.backgrounded`、`task.finished` | 创建时已知归属；排队由 Task 状态表达；子 Run 的消息/工具事件用相同目录 |
| 配置与目录 | `permission.changed`、`skill.changed`、`mcp.server_changed`、`mcp.catalog_changed` | 指明有效作用范围；目录刷新不扩张当前 Run 的已冻结能力 |
| 上下文与记忆 | `compaction.started`、`compaction.finished`、`memory.changed`、`usage.updated` | 数字来自真实报告或明确标记的估算；父子 usage 不盲目重复相加 |
| 历史与成果 | `session.committed`、`worktree.changed` | 反映权威历史提交或实际成果变化；消息完成不必等于已提交 |
| 观察 | `events.gap`、`application.closed` | 客户端需重新获取状态，或所属实例已关闭 |

成功、失败、拒绝、取消都必须让相应展示条目离开运行状态。取消会终结其作用范围内已创建但尚未执行的工具条目，不假装它们已开始。工具已成功产生的文件效果在后续取消时仍然保留其真实结果。

取消主 Run、取消一个 Task 和关闭整个 Application 是不同作用范围。保留当前前台等待超时或等待被取消后，同一个 Task 转后台继续的行为；主 Run 取消不伪造这个 Task 的取消终态。显式 tasks.cancel 才取消目标 Task，Application.close 则按现有资源关闭流程处理全部所属执行。

并发 observe Tool 的活动按照实际发生顺序显示；交给模型的批次结果继续按原请求顺序提交。分别测试两种顺序，不能用 UI 排序改变模型协议。

同一后台存活期间，每个 Run/Task/工具执行只有一次逻辑终态；传输补发可能重复，客户端通过游标去重。后台异常退出时通过实例失联/恢复快照表达未知或中断，不伪造正常完成事件。

## 7. 用户要求的完整执行树

```text
主 Run：分析项目
├─ read_file：README.md，已完成
├─ agent：委派检查测试，调用已返回 Task ID
│  └─ Task：test-reader，后台运行
│     └─ 子 Run
│        ├─ find_files：tests/，已完成
│        ├─ read_file：测试配置，已完成
│        ├─ run_command：运行检查，执行中
│        │  ├─ stdout：收集到若干测试
│        │  └─ stderr：实际产生的诊断
│        └─ 子 Agent 公开回复，持续更新
└─ 主 Agent 继续处理其他工作
```

每一行由核心事件及关联字段产生，前端不解析自然语言来猜归属。TUI 可以缩进并折叠，GUI 可以显示可展开卡片，默认精简不影响查看详情。

前台 agent 工具等待子任务期间，其子 Run 事件仍持续显示。前台等待转后台后，agent 工具可能先完成，子 Task 继续运行；子 Task 完成事件与模型 Notice 分别处理。前台等待转后台保持同一个 task_id，不创建虚假的替代任务。

观察流可以向用户展示子 Agent 的公开文字、工具调用与结果预览。主 Session 的 Transcript 和 Prompt 仍按现有语义只接收应提交的主对话、工具结果及适用的 Task 通知，不把所有子任务进度自动灌进主模型上下文。

Isolated Skill 使用同样的 Run/工具观察方式，source.kind 为 isolated_skill、task_id 为 null；仍不进入 Task 调度或获得 Worktree。

## 8. 输出、慢客户端与异常

- Shell 在进程管理层持续排空 stdout/stderr，两条流均使用增量解码，避免中文字符在块边界损坏。流标识和块偏移支持正确追加。
- 工具输出使用有界预览与可回读引用；流传输不能复制无限文本到内存。现有 result 引用随 scope 关闭可能失效，回读需明确报告过期。
- 只有 MCP 服务器实际提供可验证的进度，才发出相应 progress；否则展示调用中及终态。当前二进制结果保持现有元数据语义，图片/音频预览不是已经具备的能力。
- 投递给客户端的数据使用明确字段序列化，不直接 asdict 整个 SessionSnapshot、ToolRun 或 ModelRequest；凭据、鉴权头、Protocol Metadata 不进入展示协议。
- 观察队列与执行解耦。慢订阅者使用有界队列；相邻文字块允许合并，超出容量时明确断开该订阅并要求 resync，不能静默漏掉状态转换或阻塞所有 Agent。
- 没有前台 Run 时也有独立事件发送循环；读取请求、等待某个 Run、等待审批不能占住全部协议处理。
- 应用退出策略与窗口关闭策略分别定义。协议订阅取消只取消观察；stdio 的父进程退出/EOF 时按明确关闭流程取消所属执行并清理资源，不声称后台仍会继续。

## 9. stdio 协议交互

首版使用标准 JSON-RPC 2.0 请求/响应，服务端用 `event` notification 发送上述事件。每行一个 JSON，stdout 专用于协议，stderr 用于脱敏诊断。

客户端先 initialize，再建立订阅，再 application.open。启动可能需要项目 MCP 确认，因此协议在核心初始化完成前就要能处理 interaction.respond。长操作先返回 operation_id，后续 started/finished 事件报告实际进展，不用一个未返回请求阻止取消或审批。

请求 ID 用于配对响应；修改状态的长操作另带客户端操作键，在同一实例内识别误重发。同一键和同一内容返回已有操作，不重复创建 Run 或提交用户目标；键内容冲突返回明确错误。跨后台重启不保证自动重试安全，客户端先查询已提交历史再决定。

Python 方法、JSON Schema 与 TypeScript 客户端类型应来源一致，并用协议用例验证字段和可选值。用户不需要看到这些协议字段，界面显示业务语义。

## 10. 四步代码实施计划（待批准）

1、定义 Interface 与协议：在现有八模块依赖约束内确定操作、事件、关联、状态快照和交互登记；新增 Application 的观察与投影实现、stdio 协议目录。获批后同步 ADR、正式 Spec/Tasks/Checklist 和行为矩阵，不静默修改冻结契约。

2、打通实际事件生产：修改 `artcode/_agent/runner.py`、`artcode/_tool/catalog.py`、`artcode/_tool/subagent_adapter.py`、`artcode/_subagent/execution.py`、`artcode/_subagent/catalog.py`、`artcode/_skill/execution.py` 及 Workspace 进程输出路径。覆盖前台/后台子任务、Isolated Skill、单工具、Shell、MCP、压缩与记忆状态，保持原有协议提交和权限行为。

3、接入两个调用方式：Application 使用统一控制/查询/订阅接口；TUI 使用终端 Adapter 展示父子执行与工具活动；Python App Server 通过 stdio 暴露同一能力，并提供最小协议消费者验证 GUI 可以使用的数据。完整 Electron 产品界面另列阶段。

4、执行验证与形成验收证据：补契约、异步并发、断订阅恢复、取消清理、序列化及现有功能回归；运行真实 Shell/Git/MCP 与可配置 Provider 测试。保留用户当前未提交修改，最终记录所有实际通过、失败和外部阻塞，不能用“有最终答案”代替过程可见性验收。

## 11. 必须可观测的验收场景

- [ ] 无 UI 的协议消费者可以完成启动、审批、普通 Run、Plan/Act、取消和状态查询。
- [ ] 长工具尚未结束时已收到 started；有输出的真实 Shell 在退出前已收到至少一个输出块。
- [ ] 两个并发 Subagent 的文字和工具活动正确挂在各自 Task/Run 下，不串到主 Agent 消息。
- [ ] 子任务进入后台、父 agent 工具返回以后，订阅仍能看到该 Task 的后续工具事件及终态。
- [ ] 取消父 Run 导致前台等待退出时，子 Task 按原规则转后台并保留同一编号；只有显式取消 Task 或关闭 Application 才按对应范围终止它。
- [ ] 主 Run 结束后仍在运行的后台 Task 可以独立更新界面；读取 UI 状态不消费主模型 Notice。
- [ ] 并发工具的完成显示顺序与实际完成顺序一致，模型接收结果仍按请求顺序。
- [ ] 审批、拒绝、非法参数、超时和取消均产生可定位状态；旧审批答复不会推进已取消的操作。
- [ ] 无交互权限的 Subagent 仍按原规则拒绝，GUI 存在不扩大权限。
- [ ] Isolated Skill 实时显示公开文字和工具活动，但不新增 Task 或 Worktree。
- [ ] 展示子 Agent 过程不会增加主 Transcript 中的子任务中间文字，也不会重复投递 Task Notice。
- [ ] 订阅建立与快照间无事件缺口；有效游标重订阅可去重补齐；游标过期明确要求重新取快照，漏收工具终态后不会留下永久运行卡片。
- [ ] 慢客户端不会使其他 Run/Task 停滞，队列与输出预览受界限约束。
- [ ] 中文跨输出块、stdout/stderr 并发、MCP 无进度通知均有准确展示，不伪造进度。
- [ ] 事件和快照不包含 Protocol Metadata、配置密钥或鉴权头；敏感字段不因通用序列化进入前端。
- [ ] TUI 和 stdio 消费者通过同一套业务接口完成至少一次“主 Agent → agent 工具 → 子 Run → 文件/Shell 工具 → 子任务结束 → 主 Run 结束”的端到端场景。
- [ ] 真实 Provider 场景检查事件在任务结束前到达；不可用时记录真实阻塞，不把确定性测试冒充 live 通过。

## 12. 后续还需由用户确定的产品问题

这些问题不影响确认“所有实际执行都应可观察”，但会决定后续存储、进程和界面范围：

- 是否要求 TUI 与 GUI 同时查看、控制同一 Run。
- 关闭桌面窗口、退出整个桌面应用时，任务分别如何处理。
- 后端重启后是否仍需要查看完整子 Agent 执行树与完整工具输出。
- 第一版是否包含多个同时活动的主 Session、编辑器、文件差异或图片/音频展示。
- 新章节编号和标题，以及正式三份文档的命名。
