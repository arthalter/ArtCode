# `artcode/tui/app.py` 阅读指南

## 一、这个文件是做什么的

这个文件负责终端交互的具体实现：

- 等待用户输入。
- 把显示任务交给 Renderer。
- 在需要时向用户询问 yes/no。

它不负责决定模型该调用什么工具，也不负责判断某项操作是否危险。

可以把它理解成界面适配器。

## 二、代码结构

文件主要有两部分：

1. `UserRequestedExit`：表示用户主动退出。
2. `PromptToolkitTui`：基于 `prompt_toolkit` 的终端界面。

大部分 `show_xxx` 方法都很短，因为真正的颜色和排版在 `TuiRenderer` 中完成。

## 三、`UserRequestedExit`

```python
class UserRequestedExit(Exception):
    pass
```

这是自定义异常。

`pass` 表示类体中暂时没有额外实现。它继承了 `Exception`，所以已经可以被抛出和捕获。

为什么不直接让程序退出？

因为 TUI 只负责表达“用户请求退出”，由更高层 Runtime 决定怎样结束、是否显示退出提示以及返回什么退出码。

## 四、`PromptToolkitTui` 的初始化

类只有一个 dataclass 字段：

```python
renderer: TuiRenderer
```

dataclass 自动完成 `renderer` 的赋值。随后 `__post_init__` 创建输入会话：

```python
self._session = PromptSession(...)
```

配置包括：

- `multiline=True`：支持多行输入。
- 自定义快捷键。
- 后续行提示符 `... `。

### 补充：为什么 `_session` 没写在 dataclass 字段中

它不是由外部传入的数据，而是根据 `renderer` 和固定配置在对象创建后生成的内部状态，因此放在 `__post_init__`。

## 五、`read_input`

```python
async def read_input(self, model: str) -> str:
```

它异步等待用户输入。

使用异步输入的原因是：整个 ArtCode 已经运行在 `asyncio` 事件循环中，需要与模型流式请求、取消操作等协作。

### 异常转换

```python
except (KeyboardInterrupt, EOFError) as exc:
    raise UserRequestedExit from exc
```

`prompt_toolkit` 可能用两种底层异常表示退出。TUI 把它们统一转换成 ArtCode 自己的 `UserRequestedExit`。

`raise ... from exc` 会保留原始原因，方便调试异常链。

## 六、大量 `show_xxx` 方法为什么只转发

例如：

```python
def show_help(self, message: str) -> None:
    self.renderer.show_help(message)
```

这是委托：

- `PromptToolkitTui` 负责对外提供稳定的 TUI 接口。
- `TuiRenderer` 负责具体怎样画出来。

好处是输入会话和显示样式不会全部混在一个类里。

### 语法：`-> None`

表示这个方法不返回有意义的值。它只产生显示效果。

## 七、`confirm_tool_execution`

这是 ch06 最相关的方法：

```python
async def confirm_tool_execution(
    self,
    preview: ToolPreview,
) -> bool:
```

它循环询问：

```text
执行这个工具？(yes/no)>
```

输入 `yes` 或 `y` 返回 `True`；输入 `no` 或 `n` 返回 `False`；其他输入会继续询问。

### 语法：集合成员判断

```python
if normalized in {"yes", "y"}:
```

表示判断标准化后的输入是否属于这组允许答案。

### 语法：字符串标准化

```python
answer.strip().lower()
```

- `strip()` 去掉首尾空白。
- `lower()` 转为小写。

所以 ` YES ` 也能识别为同意。

## 八、当前确认方法存在的两个事实

第一，它已经能询问用户。

第二，当前 Agent Loop 的工具执行路径没有调用它。

这是因为 ch03 曾经设计逐次确认，ch04 为了实现自主 Agent Loop 又取消了确认，但界面方法保留了下来。

因此 ch06 可以复用这个交互入口，但需要重新设计它显示的信息和返回的决策。

## 九、为什么 `preview` 参数当前没有被使用

方法接收 `preview`，但提示文字没有展示其中的：

- 工具名称。
- 操作摘要。
- 影响目标。

这不是语法问题，而是当前功能尚未完整接线。

ch06 可以让 Renderer 先显示预览，再询问用户；或者把预览直接放入审批面板。

## 十、权限逻辑不应全部写在 TUI

TUI 适合负责：

- 展示操作详情。
- 收集用户选择。
- 返回批准或拒绝。

TUI 不适合负责：

- 判断哪个工具危险。
- 判断路径是否越界。
- 保存长期权限规则。
- 决定某种模式允许哪些工具。

否则将来换成非交互 CLI、测试环境或其他界面时，就必须复制全部权限逻辑。

## 十一、`PromptToolkitTui` 与 `TuiApp Protocol`

Runtime 中还定义了一个 `TuiApp` Protocol。它规定 Runtime 希望界面提供哪些能力。

`PromptToolkitTui` 只要实现这些同名方法，就能作为 Runtime 的 TUI 使用，不必显式继承那个 Protocol。

这也是 Python 的结构化类型思想。

## 十二、ch06 可能需要的交互结果

当前方法只返回布尔值：

```text
True  = 本次允许
False = 本次拒绝
```

如果 ch06 要支持更丰富的选择，例如：

- 允许本次
- 本次拒绝
- 本次运行内始终允许同类操作

那么简单的 `bool` 可能不够，应该用枚举或专门的数据对象表达选择。

是否需要这些能力，应先在需求阶段确定，不应仅因为技术上能做就全部加入。

## 十三、阅读练习

第一次阅读只回答：

1. 用户输入是在哪里等待的？
2. Ctrl+C 为什么会变成 `UserRequestedExit`？
3. 哪个方法能询问工具确认？
4. 真正的颜色和排版在哪里？
5. 为什么权限规则不应该直接写进这个文件？
