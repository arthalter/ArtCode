# ch11：Agent 评测与审计闭环 Spec

## 背景

ArtCode 已经具备流式 Agent Loop、本地工具、权限规则、macOS Seatbelt、MCP、上下文压缩、会话恢复和长期记忆。现有测试能证明单个模块和已知链路按预期工作，但还不能系统回答“Agent 是否完成了任务、付出了多少轮次与 Token、哪个系统机制带来了收益、版本修改后是否退化”。

本章建设一个独立于被测 Agent 的 Eval Harness。它从版本化 Benchmark 启动真实 ArtCode 任务，收集运行轨迹，使用确定性验证器判断结果，可选使用无工具 LLM Judge 评估语义质量，并输出可对比的机器报告与人类报告。评测主线聚焦 ArtCode 的两个核心系统：工具权限与长上下文治理，同时覆盖任务结果、恢复可靠性和运行成本。

## 目标用户

- 需要用可重复数据判断 ArtCode 修改是否真正改进的项目作者。
- 希望学习 Coding Agent 的 Benchmark、Run Trace、Verifier、LLM Judge 和回归对比的开发者。
- 需要在本地、可审计环境中验证权限边界和上下文治理效果的用户。

## 目标

- 建立与被测 Agent 分离的本地评测运行器，不让 Agent 自证已完成任务。
- 用版本化 Benchmark 固定任务、工作区初始状态、验证规则和可选语义评分标准。
- 对每次 Agent 运行保留脱敏、有序、可回放的 Run Trace，支持从结果追溯到模型轮次、工具调用、上下文处理和终止原因。
- 同时给出任务结果、工具与权限、上下文、恢复、效率与成本指标，不用单一通过率代替系统判断。
- 将确定性验证作为结果真值，LLM Judge 只负责难以用规则表达的语义质量，不能覆盖确定性失败。
- 生成可供程序消费的完整报告和可直接阅读的 Markdown 摘要，并支持两份报告的回归对比。

## 功能需求

### Benchmark 定义与校验

- F1：评测工具能从人类可读的版本化文件加载一组任务，每个任务明确包含身份、用户请求、初始工作区、执行边界、重复次数和验收规则。
- F2：在任何 Agent 或验证器运行前完成整份 Benchmark 校验；重复任务身份、越界路径、未知验证类型、非法限制或结构不完整时不得启动部分评测。
- F3：每份 Benchmark 在报告中具有内容指纹与来源信息，使后续结果可精确关联到当时使用的任务定义。

### 隔离运行与 Agent 执行

- F4：每个评测尝试在独立的临时 Workspace 中运行，初始工作区只被复制、不被原地修改；同一任务的重复运行之间不共享会话、记忆或文件修改。
- F5：评测运行器使用 ArtCode 当前生产 Agent 主链路执行任务，不实现第二套简化 Agent；超时、取消、模型失败、工具失败和验证失败都作为当次尝试的结果记录。
- F6：单个尝试失败不阻断其他任务；用户中断整体评测时，已完成尝试与当前部分状态仍然能保留为可诊断证据。

### Run Trace 与评测证据

- F7：每次尝试产生一份按顺序追加的 Run Trace，至少记录运行身份、相对时间、Agent 轮次、工具批次与结果、Token 用量、上下文处理事件和终止原因。
- F8：Trace 对工具参数和输出使用有界预览和稳定指纹，足以识别重复调用与追溯失败，但不直接保存认证秘密、完整大文件或无界模型输出。
- F9：Trace、确定性验证结果、语义评分和最终报告共享可追溯的运行与任务身份，不依赖文件名或执行顺序猜测对应关系。

### 验证、Judge 与指标

- F10：确定性验证器能检查命令退出状态、文件存在性、文件缺失性和文本内容，并以结构化结果记录每项通过、失败、耗时和有界证据。
- F11：可选 LLM Judge 使用独立的无工具请求和固定评分标准，只读取当次尝试的最终回复、文件变更摘要与确定性验证结果；格式错误、超时或模型失败必须显式显示为 Judge 不可用，不伪造默认高分。
- F12：每次尝试统计任务结果、验证器通过率、模型轮次、工具调用数、工具失败数、重复调用数、权限拒绝数、上下文压缩前后用量、Token 用量、耗时和可选 Judge 分数。
- F13：汇总报告按任务与整体分别展示成功率、失败分布、平均与极值效率指标；没有可用样本的指标显示为不可用，不以零冒充真实观测。

### 报告、对比与 CLI

- F14：每次评测产生一份自包含机器报告和一份 Markdown 报告，包含 Benchmark 指纹、代码版本、脱敏模型配置、尝试状态、验证证据、运行指标、失败摘要和产物路径。
- F15：评测工具能对比两份兼容报告，按任务和总体输出成功率、Token、轮次、工具调用、重复调用、耗时和 Judge 分数的变化，明确标出改进、退化和无法比较。
- F16：独立命令行入口至少支持校验 Benchmark、运行评测和对比报告；各命令使用明确退出码区分成功、评测不通过和工具自身无法运行。

## 非功能需求

- N1：评测在本地运行，除明确配置的被测模型与 Judge 请求外，不向外部服务上传 Workspace、Trace 或报告。
- N2：被测 Agent 仍经过 ArtCode 现有权限、路径、危险命令和 Seatbelt 边界；评测工具不提供绕过安全边界的隐藏通道。
- N3：工作区、任务定义、输出根目录和配置路径必须在执行前解析与校验，拒绝符号链接越界、输出覆盖输入和对非评测目录的广泛删除。
- N4：相同 Benchmark、初始工作区、模型配置和外部响应应产生相同的任务顺序、验证顺序、指标定义和报告结构。
- N5：所有报告都明确区分观测值、计算值、缺失值和 Judge 主观值，不将测试用例数、重试或未执行项冒充成功指标。
- N6：Trace 和报告的文本字段全部有界，已知 API Key、认证头、MCP 秘密和工具中的常见秘密形式在落盘前脱敏。
- N7：单个任务、Verifier 或 Judge 的失败局部隔离，已经完成的结果采用原子替换保存，评测进程中断后不需要重做已完成证据才能排查。
- N8：默认报告足以在终端和代码审查中阅读，不要求 Web 服务、数据库、外部可观测平台或常驻后台进程。
- N9：现有 ArtCode CLI、Agent Loop、权限、上下文、会话、记忆、MCP 和测试行为保持兼容；评测能力通过独立入口接入。
- N10：核心解析、指标、验证和报告不依赖真实 API；真实 DeepSeek 任务作为独立 Live 验收，失败时与确定性回归分开报告。

## 设计骨架

1. **Benchmark 目录**：负责任务定义、初始工作区引用、验证规则、可选语义标准和内容指纹。
2. **隔离运行器**：为每次尝试复制 Workspace，经当前生产主链路执行 Agent，控制超时与失败隔离。
3. **Run Trace 记录器**：将 Agent 事件、工具结果、Token、上下文状态与终止状态持久为脱敏有序证据。
4. **确定性 Verifier**：在被测 Workspace 上执行文件与命令检查，输出结构化真值。
5. **可选 LLM Judge**：对最终回复、变更摘要和 Verifier 结果进行无工具、固定 Rubric 评分。
6. **指标与报告**：从 Trace 和验证证据计算任务、过程、上下文、权限、恢复和成本指标，生成 JSON、Markdown 和回归对比。
7. **独立 CLI**：提供 Benchmark 校验、评测运行和报告对比入口，不将评测命令混入交互式 Agent 会话。

## Out of Scope

- 不构建 Web Dashboard、多用户评测平台、分布式执行器、队列服务或远程产物存储。
- 不自动生成 Benchmark 任务，不让被测 Agent 改写评测定义或评分标准。
- 不把 LLM Judge 作为确定性真值，不允许 Judge 调用工具、修改 Workspace 或忽略 Verifier 失败。
- 不评测模型底层推理性能、GPU 吞吐、量化、微调、LoRA、PPO 或 GRPO。
- 不在本章增加 RAG、Skills、Subagent、Agent Team 或新的编码工具。
- 不为了获得更高评测分数放宽现有权限、危险命令、路径或 Seatbelt 边界。
- 不将评测运行自动上传到云端，不在报告中存储未脱敏认证信息。

## 验收标准

- AC1：合法 Benchmark 可通过校验并产生稳定指纹；任务重名、越界初始目录、未知验证类型和结构缺失均在运行前失败。
- AC2：一次评测不修改 Benchmark 初始工作区，每个重复尝试拥有不同 Workspace、会话和产物路径。
- AC3：至少一个真实 ArtCode 编码任务从 Benchmark 执行到验证结束，生成可读 Trace、JSON 报告和 Markdown 报告。
- AC4：权限场景中的越界路径、危险命令或明确拒绝能在 Trace 与指标中观测，且评测不会因为需要高分而绕过安全策略。
- AC5：上下文场景中能观测工具结果外置或压缩事件、压缩前后用量，并证明当前任务请求仍完整存在。
- AC6：文件、文本和命令 Verifier 同时覆盖通过、不通过、超时和执行失败，且一项失败不隐藏其他验证结果。
- AC7：开启重复运行后，报告保留每次原始结果并给出聚合成功率、平均 Token、平均轮次、平均工具调用和平均耗时。
- AC8：LLM Judge 未启用时不影响确定性评测；启用后只接受符合固定结构与分数边界的结果，其失败显式记录为不可用。
- AC9：两份兼容报告可产生包含改进、退化和不可比较项的对比报告，Benchmark 指纹不同时默认拒绝直接比较。
- AC10：任意单任务失败后后续任务继续；整体中断后已完成 Trace 和尝试结果仍然可读。
- AC11：使用含已知秘密的配置、工具参数和模型输出运行脱敏测试后，Trace、JSON、Markdown 和终端摘要均不包含原始秘密。
- AC12：新增评测能力不改变原 ArtCode CLI 的启动、普通会话、Plan/Do、权限、上下文、会话恢复、记忆和 MCP 行为，现有回归测试保持通过。
