# ch12：Skill 系统 Plan

## 架构概览

ch12 新增独立的 `skills` 领域层，负责 Skill 文件发现、解析、优先级覆盖、热更新、激活状态和目录诊断。它不直接拥有 Agent Loop、权限或文件执行能力；运行时通过只读快照向提示词组装层提供目录、激活 SOP 与工具白名单，通过一个受控的系统级加载工具改变激活状态。

```
项目 / 用户 / 内置 Skill 目录
  → Skill 发现与解析
  → 目录快照（名称、说明、来源、诊断）
  → 激活状态（完整 SOP、模式、白名单、最后有效版本）
  ├─ 请求组装：目录提示 + 激活 SOP + 收窄后的工具集合
  ├─ 加载工具：按名字激活 Skill
  ├─ 命令入口：/<skill-name> 同轮加载并执行
  └─ 执行协调：共享主会话 / 隔离子会话
```

现有权限、Plan/Do 工具模式和 ToolExecutionService 继续是真正的执行许可边界。Skill 白名单只提供“模型看得见、执行器也接受”的更窄一层限制，不能扩大现有模式能力。

## 目录与来源

| 来源 | 根目录 | 优先级 | 用途 |
|---|---|---:|---|
| 项目 | `<workspace>/.artcode/skills/` | 1 | 与当前项目一起维护的 Skill |
| 用户 | `~/.artcode/skills/` | 2 | 用户在多个项目复用的 Skill |
| 内置 | 包内只读资源目录 | 3 | 未来可随 ArtCode 交付的通用 Skill |

单文件 Skill 位于来源根目录的 `*.md` 文件；目录型 Skill 使用 `<name>/SKILL.md` 作为唯一入口。扫描只识别这两种入口，不递归把模板、示例、脚本和参考文档当作 Skill。所有候选路径均须是来源边界内的普通文件，符号链接、不可读文件、非 UTF-8 文本和不合法 YAML 产生单项诊断。

发现器按“来源优先级、规范化名字、路径”排序，先在同一来源检测重复身份，再执行跨来源覆盖。它产出不可变目录快照，而非让调用方依赖字典或文件系统遍历顺序。

## Skill 数据模型

`artcode.skills` 以不可变值对象表达以下概念：

| 概念 | 关键内容 | 规则 |
|---|---|---|
| Skill 来源 | 项目、用户、内置及入口路径 | 仅用于优先级、诊断和热更新 |
| Skill 元信息 | 名字、说明、普通工具名、执行模式、历史轮数、可选模型 | 由 frontmatter 严格解析 |
| Skill 定义 | 元信息、SOP 正文、能力包根、资源清单、文件指纹 | 只有有效定义可被激活 |
| Skill 目录 | 有效定义、被覆盖项和诊断 | 启动阶段只暴露名字与说明 |
| 激活项 | 定义快照、激活顺序、当前请求的一次性模型选择 | 完整 SOP 从这里进入每轮请求 |
| Skill 运行快照 | 目录摘要、激活 SOP、可见工具名交集、系统加载工具、待独立执行请求 | 请求组装与执行协调共用 |

frontmatter 接受且只接受 `name`、`description`、`tools`、`mode`、`history_turns`、`model`。名字使用可安全映射为斜杠命令的规范小写标识；说明必须是一句非空文本；工具为无重复字符串列表；模式为共享或独立；独立模式的历史轮数为非负整数，省略时为 0；模型为可选非空文本。共享模式声明历史轮数、未知字段、错误类型或互相冲突的值都形成单项解析诊断。

## 发现、刷新与激活状态

`SkillService` 持有最后一次有效目录和激活项。启动时它完成一次严格发现：单文件解析错误可跳过；成功解析但引用未知普通工具是启动错误。启动完成后，每次准备新的用户请求前比较入口与能力包的文件指纹并刷新目录。

运行时刷新采用“候选快照 → 全量校验 → 原子替换”流程：

- 新版本有效时替换目录；同名激活项改为新定义，下一次请求使用新 SOP。
- 某个已激活版本更新后变得无效时，保留该 Skill 的最后有效激活定义，并发布诊断。
- 新增或未激活 Skill 变得无效时，不进入目录，不影响其他 Skill。
- 删除已激活 Skill 时，最后有效激活定义仍保留到清空对话；目录不再提供新的加载入口并发布诊断。

清空对话调用 SkillService 的清理入口，移除全部激活项和一次性执行信息；它不修改磁盘中的 Skill 文件。

## 提示词与两阶段加载

请求组装层从 SkillService 获取每轮运行快照，并使用三个瞬态系统消息：

1. **Skill 目录消息**：只包含已发现 Skill 的名字与一句说明，固定在基础系统提示之后。
2. **激活 Skill 消息**：按激活顺序包含完整 SOP，使用明确的 `<active-skills>` 边界，置于目录消息之后、会话历史之前。
3. **既有运行时提醒**：继续由当前模式与工具可见性生成。

这些消息不写入 Conversation，也不参与历史压缩或会话持久化；每次真实请求、只读估算、压缩后的重组和紧急重试都从同一 Skill 运行快照重新构建。未激活 Skill 的 SOP 和能力包资源绝不进入请求。

用户输入 `/skill-name 附加要求` 时，动态命令解析器先查询当前目录：找到 Skill 后走统一激活与执行协调；找不到时回退现有命令的未知命令提示。Skill 成功加载后，动态命令注册表向帮助系统公开该短命令，而不是覆写静态内置命令。普通自然语言请求仍先进入 Agent Loop；模型可从目录消息调用加载工具自行选择 Skill。

## 系统级加载工具与白名单

新增 `load_skill` 系统工具。它只接收目录中存在的名字，通过 SkillService 激活对应定义，并返回受限的加载结果；不能按任意路径读取文件。工具声明为系统来源、只读、不可写永久权限规则，执行器对它跳过常规文件审批，但仍保持结构化调用、错误结果、取消和审计语义。

ToolOrigin 与 ToolAccessPolicy 扩展为同时表达“系统工具”“模式效果限制”和“按名字的可见集合”：

- 正常会话无激活 Skill 时保留全部既有普通工具与加载工具。
- 已激活 Skill 时，普通工具名只能落在所有激活白名单的交集；`load_skill` 始终补回。
- Plan/Do 继续先应用既有效果限制，Skill 名称限制只会继续收窄。
- ToolExecutionService 使用同一组合策略复核调用，避免模型伪造未展示工具名绕过白名单。
- 权限审批、危险命令检查、Seatbelt、路径政策和 MCP 审批保持原链路；加载工具不会授予其他工具额外能力。

## 执行协调

`SkillExecutionCoordinator` 是斜杠入口和加载工具后的统一编排点。它将用户的斜杠附加文字作为本轮用户要求追加给模型，而不是替换 SOP 中的模板位置。

### 共享模式

协调器激活 Skill 后沿用当前 Conversation、AgentLoop、ToolExecutionService 与持久化观察者继续执行。自然语言路径中，模型调用加载工具后，下一个 Agent Loop 请求看到完整 SOP 和收窄工具；斜杠路径中，协调器在同一轮以附加要求启动主 Agent Loop。Skill 指定模型仅在这个执行周期的后续模型调用中生效。

### 独立模式

协调器从主 Conversation 选取最近 N 个完整历史单元（用户消息及关联 Assistant/Tool 记录），创建不绑定会话日志、长期记忆观察者或主上下文压缩状态的临时 Conversation。临时 Agent 继承基础系统提示、当前已激活 Skill、组合后的工具限制、权限服务、路径政策和 Seatbelt；工具结果与中间回复都只留在临时 Conversation。

独立 Agent 的最终回复按 Skill SOP 作为简洁总结生成。协调器仅将原始用户请求和最终总结写回主 Conversation；子对话的工具调用、原始工具输出、推理与中间回复不回流。子任务出错或取消时，主会话保留可诊断的失败摘要，不损坏既有历史。指定模型由 ProviderRequest/StreamCollector 一路传递到 Provider payload，仅作用于该独立执行。

## 目录型资源

加载入口只读取 `SKILL.md` 正文并返回能力包资源清单。模板、示例、脚本和参考文档不自动注入、执行或被解释为可执行权限；它们随目录一起保存，供未来明确的资源访问能力或用户维护使用。ch12 不新增任意能力包脚本执行机制，也不扩展现有工作区文件权限到用户级或内置 Skill 目录。

## 关键技术决策

| 决策 | 选择 | 理由 |
|---|---|---|
| Skill 正文输入 | 直接注入 SOP 与用户当前要求 | LLM 已有上下文理解能力，避免学习型项目引入模板语言 |
| 加载时机 | 目录摘要启动注入，完整 SOP 按需加载 | 控制初始上下文和工具描述规模 |
| 多 Skill 工具集合 | 普通工具白名单取交集 | 任一激活 Skill 都不能被另一份 Skill 放宽 |
| 更新机制 | 每个新请求前指纹刷新 | 无后台线程、保存后立即生效且可测试 |
| 运行中无效更新 | 保留最后有效激活版本 | 不把编辑中的暂时错误变成会话中断 |
| 独立模式记录 | 只回流最终总结 | 保持主对话可理解，隔离中间工具噪声和失败细节 |
| 目录包资源 | 分发但不自动访问/执行 | 避免资源注入膨胀和越过工作区安全边界 |
| 具体 Skill | 不内置、不特化 | 保持系统通用，不把示例工作流固化进核心代码 |
